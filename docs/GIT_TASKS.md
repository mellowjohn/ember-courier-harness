# Reviewed Git browser repairs

Ember can retain a local Git history for an exact browser-game repair and check
the same saved regression against clean named before and after builds. It uses
the existing project scope, owner-review inbox, gate, audit, task attempts,
Chromium driver and exact game-application review. Exact source edits need no
model call. The optional automated repair entry uses the existing approved Muse
coding worker and independent reviewer before preparing the same exact Git
permission packet.

The supported source family is the existing flat offline HTML/CSS/JavaScript
browser target. Start with the current approved game or the exact files from a
reviewed workspace import. Importing or selecting files is not permission to
write the original repository. The Git operation always uses new private
repositories inside the session's ignored `git-runs/` directory.
On Windows, preparation requires projected private Git branch/reflog lock paths
to fit within 248 UTF-16 code units. It refuses longer project locations before
creating a run, with guidance to choose a shorter Ember workspace. Attached
source repositories can remain in their original location. Git's `longpaths`
option does not reliably remove the installed Windows Git reference-backend
limit; no drive mappings, junctions or writes outside the approved workspace are
used to bypass it.

## Review, verify and apply

1. Approve a project scope and select its task. A scope created before Git
   permissions were introduced needs a separately reviewed amendment or renewal.
2. Save gameplay checks demonstrating the problem. The same frozen plan must
   fail on the starting build and pass on the proposed repair. Existing limits
   are four scenarios, 32 steps per scenario and a 90-second action
   budget.
3. Prepare exact source changes in the Git repair tools. Review the changed
   file diff, source origin, complete proposed bytes, frozen checks and worker
   and verifier permissions. Preparation creates no Git repository and starts
   no worker, provider or game write.
   A pending Muse source proposal can also be sent through Git verification.
   Its exact candidate, starting files and project/task binding are frozen;
   verifying it makes no additional model call. A qualified head returns to the
   same pending build review instead of duplicating it. Declined, applied or
   changed proposals cannot be revived through this route.
4. Approve the worker and verifier contracts. The host initializes a fresh Git
   baseline from the reviewed source. A distinct verifier checks a clean copy
   of that named commit using the fixed Chromium driver. If the required
   baseline regression does not fail, the run stops before creating a candidate.
5. The worker commits only the exact reviewed candidate. Its local commit has
   `Round`, `Contract-Id`, `Contract-Version`, `Contract-Hash` and `Subsystem`
   trailers and passes the existing Git-aware `contract-lock`. Another clean
   copy of that head runs the identical frozen checks. Failed gameplay, startup,
   browser observations or layout checks prevent recommendation.
6. Inspect the retained game and bound screenshots. **Review exact changes**
   prepares a normal build proposal; it does not apply the repair. Exact build
   approval and separate task-outcome acceptance retain their existing paths.

The source import, the current game and any original `.git` directory remain
unchanged throughout Git verification. The new history records an isolated
reviewed source snapshot and its repair; it does not preserve or claim ancestry
from an original repository's complete history. The original source location is
provenance context, not authority or an independent identity attestation.

## Automated browser repairs

Open **Project tools → Plan → Local Git repairs → Review automated Git repair**.
The selected approved task describes the repair; its saved gameplay checks must
already demonstrate a failure on the starting game. A non-reproducing baseline
ends the allocated attempt before any coding call. This is a browser-source
repair workflow, not permission to run an imported repository's commands.

1. Review the existing task worker and separate verifier contracts. Muse sees
   the frozen task, approved design, current source, brief and checks. Generated
   source stays isolated in `task-runs/`; the worker can repair failed candidates
   within the existing attempt, time and shared promotional-credit limits.
2. A qualified source report automatically prepares an exact Git review. Review
   its full source diff, frozen checks, worker/verifier permissions and source
   handoff. Preparing this next packet grants no Git permission. Interrupted
   preparation can be resumed with **Review generated Git verification**.
3. Approve the exact local Git repair. The existing worker creates clean named
   baseline/head builds and the independent verifier runs the same frozen
   regression. No model call or new source generation occurs in this stage.
4. Review the Git candidate and captures, then separately review and approve the
   exact game application. Task acceptance remains a later human decision.

The source and Git stages use **one existing allocation**. A qualified source
report leaves that allocation open through clean Git verification. Ordinary task
allocations finish when verification succeeds, fails or is stopped. A canonical
finding's successful attempt remains open until explicit C3 closure or owner
cancellation. Declining Git permissions cancels the original allocation; it
cannot generate a free retry. A generated task has at most one Git handoff.
The handoff binds source run/index/report hash, original/candidate bytes,
project scope, task identity and saved checks. Changed reports, source, scope,
checks or stopped source runs cannot be redirected into execution or promotion.
The ordinary task promotion endpoint refuses marked Git repairs, so its source
pass cannot substitute for the required clean Git witness.

If a recorded decline is interrupted before its bookkeeping finishes, use
**Complete cancellation**. After declining the final application of a finding
repair, use **End discarded repair** to end that same still-open attempt. After
a scope change, **Discard inactive task review** or **End inactive task run**
ends the old review/run. These explicit controls preserve its evidence and
consumed allowance; merely viewing a card does not cancel work or release it.

### Canonical finding bridge

An existing reviewed finding also offers **Review Git repair agent**. It uses
the same finding identity, frozen bug snapshot, selected regression and existing
canonical bug attempt. The source worker reproduces that assertion before
coding. Git verification does not manufacture another bug or allocate another
finding attempt. A failed clean Git witness ends that same attempt; escalation
still uses the canonical owner decision and state hash.

After passing clean Git verification and exact application, **Review verified
closure** retains the existing explicit C3 owner action. Its packet and closure
record include the named Git base/head and report hash. Historical closure,
contract-lock and project handoff recheck the source report, clean commits,
captures and explicit owner receipt. Changed Git evidence invalidates that
closure witness. S0/S1 closure remains Johnathan-only even under `approve_all`.
This connects the browser finding's C0 snapshot, C1 independent source report,
C2 clean Git/exact-application witness and explicit C3 closure; general library
round decomposition and failure-driven scope amendments remain separate work.

## Attempts, recovery and evidence

One ordinary Git run allocates one attempt from the selected task's existing
`TaskAttempts` identity. Canonical finding repairs use their existing bug-attempt
ledger instead. The source and Git stages share the applicable allowance.
A new run, renamed repair goal or project-scope renewal cannot reset it.
Non-reproducing baselines and failed heads consume their allocated attempts.
The existing explicit owner decision is required after the allowance is exhausted.
The Git card shows that shared allowance and offers an explicit one-extra-attempt
or stop decision when no allocation is running. That accounting decision does not
prepare work, approve contracts or start a worker. A changed state hash refuses
stale or repeated decisions.

Completed source writes, local Git phases and captures are retained through the
existing gated checkpoint executor. An interrupted run reuses the same attempt,
immutable file bytes and completed named commits. Source, plan, authority,
runtime or input changes stop execution rather than silently redirecting work.
Partial browser output still needs inspection; it is not erased or automatically
replayed with different inputs.
If interruption follows the audited final report, resume rechecks that evidence
and finishes the same attempt's allowance and status receipts. It does not create
another commit, capture, report or attempt.
Audited review packets also recover missing initial control metadata. Only a
verified recorded request can supply a missing reference, and the original plan
must remain exact. Initial status derives from existing owner receipts; partial
contract receipts alone never approve a batch. Conflicting control files are
refused. An expired or renewed scope still permits discarding a pending review;
approval and execution require the current exact scope.

The report binds baseline/head commit IDs, both source manifests, the saved
gameplay-plan hash, author/verifier identities, browser captures and contract-lock
results. Preview, screenshot reads, promotion and export recheck the retained
files, Git builds, captures and checkpoints. Changing a report, metadata,
configuration, source file or screenshot refuses access to purported passing
evidence. ZIP export contains the candidate browser files and a compact Git
verification record, without original Git metadata or private approval history.

The Git helper clears inherited Git redirection/configuration variables and
disables transport, hooks, credential helpers, fsmonitor, attribute configuration,
signing and automatic maintenance. Imported `.git` files, remotes, hooks,
attributes, config filters and repository-native test scripts are never copied
or executed. Browser source runs only through the existing network-blocked
Chromium preview. The verifier cannot edit game source; its write paths hold
capture inputs and evidence only.
Canonical mechanic references also freeze their source profile. Changing the
reference runtime or controls blocks qualification even if DOM checks report a
pass and the edit suppresses mechanic observations. The report explains the
source blocker; preview, promotion and export recheck that review.

## Working boundary

This provides exact edits or an approved model-to-Git browser repair with a
deterministic clean-build verifier. It does not launch a general repository
coding agent, execute arbitrary repository
commands or native/Python tests, modify source repositories, push, create PRs,
publish, deploy or integrate an engine. Passing DOM checks are game-influenced
observations and do not prove complete gameplay correctness, artistic quality
or human acceptance.

The original `Rounds` flow remains tied to canonical bug identities and explicit
verified closure. The automated browser finding bridge above reuses those
existing finding/attempt/closure rules without replacing its Git report for C3.
General repository rounds and failure-driven scope amendments remain separate
integration work. S0/S1 closure still requires Johnathan's own decision.

Implementation: `git_task.py`, the narrow Git helper in `contract_lock.py` and
the existing `polish.Worker` executor. Focused checks:

```powershell
py -3.12 tools/offline_tests.py --pattern test_git_task.py
py -3.12 tools/git_task_check.py
py -3.12 tools/git_task_check.py --ui
py -3.12 tools/git_task_check.py --ui --form
py -3.12 tools/offline_tests.py --pattern test_git_automation.py
py -3.12 tools/git_automation_check.py
py -3.12 tools/git_automation_check.py --finding
```

The unit tests use real private Git repositories and owner/browser fixtures.
`git_task_check.py` additionally runs real Chromium keyboard/touch/reset checks,
the existing-proposal bridge, capture-tampering refusal, deterministic export
and separate exact application. `--ui` uses the actual permission card,
background worker, candidate preview, before/after images and exact apply
controls. `--ui --form` exercises the exact source edit form instead of the
pending-proposal bridge. Both leave human task acceptance pending. The rehearsal
also renders a clearly synthetic exhausted-attempt state to check the extra
attempt control and intercepts its submission; real allowance decisions are
covered by the offline API tests. The rehearsal denies unstubbed provider
reservations and uses synthetic owner decisions.
Reports and screenshots remain under ignored `.harness/git-task-checks/` and
`.harness/git-automation-checks/`. The isolated synthetic projects use short,
uniquely created `.harness/g…/` or `.harness/a…/` folders in the same checkout,
retained and identified in their reports.
These checks establish the bounded fixture's observed behavior, not live-model
quality or complete gameplay correctness.
